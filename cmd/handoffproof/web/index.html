About HandoffProof

What problem this project addresses, how it addresses it, what exists today, what has been measured, and what comes next.

The problem

Software rarely fails the day it is written. It fails the day its author leaves - when a credential only they held is withdrawn, a configuration value only they knew goes missing, or a backup nobody tested turns out to be incomplete. The knowledge was never in the repository; it was in a person.

Documentation does not close this gap by itself, because documents describe what someone believed, not what the system does. A handover document can say the reminder job is configured while the variable it needs is documented nowhere.

In one line: HandoffProof rehearses the developer's exit and proves, with observed evidence, whether the application survives it.

Our approach

A deterministic Go controller owns every verdict. It copies the application into an isolated Docker sandbox, injects a failure (a withdrawn token, a missing configuration, an incomplete backup), and asserts real workflows - a user row exists, a booking persists, exactly one confirmation email arrived. Each assertion becomes an evidence record.

A Meta-model agent works around that core. It reads the static scan, proposes dependency maps, diagnoses failures from controller evidence, and drafts repairs. It never issues a verdict, never writes evidence, and never touches protected paths: acceptance tests, the controller, and the evidence format are hash-frozen and verified before and after every run.

Core contribution

The contribution is the separation of judgement from generation. Language models are fluent and often right, which makes their errors hard to spot. HandoffProof lets the model do what it is good at - reading, explaining, proposing - while a small deterministic core decides what is true, and can prove it with evidence a third party can re-run.

Executed and verified

  • Four controller drills (baseline, withdrawn token, missing configuration, incomplete backup) run end to end in isolated sandboxes; the three fault drills fail exactly the assertion they were designed to break.
  • The independent Playwright acceptance suite passes 4/4 on the healthy baseline and goes red when the token is withdrawn - then green again after a controller-applied repair and identical rerun.

Scope

In scope

  • Single-operator handover rehearsal for containerized applications like the bundled demo app.
  • Failure classes: withdrawn credentials, undocumented configuration, incomplete backups, silent failures, documentation gaps.

Not in scope today

  • Multi-tenant or multi-user operation; the console uses one shared token by design.
  • Attackers with local filesystem or Docker-daemon access to the host machine.
  • Automatic push or pull-request creation - remediation stops at a reviewed, dry-run diff.

Known limits

  • Prompt injection can influence model text. It cannot influence verdicts, evidence, or accepted repairs; those gates are deterministic.
  • Secret redaction is pattern-based defense in depth. The hard boundary is that credential files are never read into model context at all.
  • Container images are pinned by tag and lockfile, not yet by digest.
